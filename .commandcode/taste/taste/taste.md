- Treats `schema.sql` as the source of truth: when a fix was applied ad-hoc in the Supabase SQL Editor, wants it back-ported into the file (e.g. "tambahkan di schema.sql nya") rather than left only as a manual query. Confidence: 0.55
- Writes SQL migrations defensively/idempotently (`add column if not exists`, `drop constraint if exists`, seed `insert ... where not exists` / `on conflict do nothing`) so they can be re-run safely. Confidence: 0.55
- Writes code comments and user-facing content (lesson/task text, seed data) in Indonesian, matching the app's audience. Confidence: 0.6
- Wants production/operations knowledge captured as a Markdown notes file committed in the repo (e.g. `CATATAN-PRODUKSI.md` covering env vars, deploy flow, DB updates, limits, troubleshooting) rather than left only in chat. Confidence: 0.5
- Communicates terse, casual prompts (e.g. "fitur selanjutnya?") and is comfortable letting the agent pick and execute the next highest-value piece of work autonomously rather than answering multiple-choice questions. Confidence: 0.65
- Expects work to be finished by committing to git and pushing to GitHub (`git push origin main`) once the change is verified, not left as an uncommitted local diff; explicitly asks for this ("commit dan push ke github"). Confidence: 0.65
- Deploys via Vercel with auto-deploy wired to GitHub `main`, so pushing to main is the deploy step (DB migrations still run manually in Supabase SQL Editor). Confidence: 0.5
- Prefers fixing a UI/behavior gap consistently across *all* affected surfaces rather than patching only the screen first mentioned (when asked whether to fix the student dashboard, the task list, or both, chose "Keduanya"/both). Confidence: 0.45
- When handed a list of findings/issues, wants the highest-severity/highest-priority ones fixed first ("perbaiki sekarang yang menjadi prioritas tinggi dulu") rather than a broad sweep or lowest-effort items. Confidence: 0.5
- Builds a learning app for grade 9 SMP (junior high) Python beginners; expects student-facing instructions, help material, and messages written in simple Indonesian for that audience, exercises limited to concepts already taught (e.g. only variables + `print()`, no input/if/loop/list/function), and difficulty increasing progressively. - Wants strong pedagogical guardrails so students can't shortcut exercises: challenges locked in strict sequence until the previous one is correct, target output not selectable/copyable, solution/reference code never shown to students (kept internal for validation only), and wrong answers get simple hints instead of the answer. Confidence: 0.7
- Wants such student constraints enforced authoritatively on the server (locked levels rejected even when the URL is entered directly, grading recomputed server-side) rather than only hidden in the UI. Confidence: 0.55
- When extending the app, prefers slotting new content into the existing feature/route (e.g. a new module inside the existing `/siswa/lab` area) over building a parallel new page/route. Confidence: 0.5
- When adding a feature, explicitly asks that already-working functionality be preserved ("Pertahankan fitur: autosave jawaban, progres tantangan, tantangan terkunci ...") rather than regressed by the change. Confidence: 0.5
- Wants student-facing UI polished for visual quality and ease of reading, not merely functional. Confidence: 0.8

Confidence: 0.55
- Wants explicit loading feedback on every page transition/redirect (link clicks, back/forward, server-side `redirect`), not just backend calls, so the user knows their click registered and the next page is loading ("setiap redirect ke halaman yang berbeda / berpindah halaman tambahkan status loading").
